## 1. What's new in Lab 11?

Open `std::vector`'s documentation: `std::vector<int>`, `std::vector<double>`, `std::vector<string>`, `std::vector<Shape*>` — they all work. Yet the standard library does **not** ship four separate vector classes. There is one piece of code, parameterised over its element type. That mechanism is a **template**.

You have used templates the entire course (every `vector<…>`, every `unique_ptr<…>`, every `shared_ptr<…>`). This lab is about writing your own.

New concepts introduced in this lab:

- **Function templates** — one function recipe, many concrete versions generated by the compiler.
- **Type deduction** — the compiler figures out the template arguments for you.
- **Class templates** — the same idea applied to whole classes.
- **Non-type template parameters** — values (like sizes), not just types.
- **Template specialization** — overriding the generic behaviour for a specific type.
- **Templates + polymorphism** — how generic code and `virtual` functions complement each other.

All examples live in `templates.cpp` — read it side-by-side with this document.

## 2. The motivating problem

Suppose you need a function that returns the larger of two values. You write it for `int`:

```cpp
int maxInt(int a, int b) { return (a > b) ? a : b; }
```

Then you also need it for `double`:

```cpp
double maxDouble(double a, double b) { return (a > b) ? a : b; }
```

Then for `string`. Then for `Date`. Three, four, five copies of the **same logic**, with the only difference being a type name. Every bug fix has to be made in every copy. Every new type needs a new function.

That repetition is what templates eliminate. A template lets you write the function *once*, with the type as a parameter:

```cpp
template <typename T>
T maximum(T a, T b) { return (a > b) ? a : b; }
```

The compiler generates a fresh function body for every concrete type you actually use it with. **You write the recipe; the compiler stamps out the dishes.**

## 3. Function templates

The syntax is:

```cpp
template <typename T>
T maximum(T a, T b) {
    return (a > b) ? a : b;
}
```

`template <typename T>` declares a template parameter named `T`. Inside the function, `T` behaves like a type name. (`class` works too: `template <class T>` means exactly the same thing. `typename` is the modern, preferred spelling.)

Calling the template is exactly like calling a regular function:

```cpp
maximum(3, 7);          // T = int    → returns 7
maximum(2.5, 1.7);      // T = double → returns 2.5
maximum<string>("cat", "dog");   // T = string → returns "dog"
```

The compiler sees `maximum(3, 7)`, figures out that `T = int`, and **instantiates** a copy of the function with `int` substituted everywhere. The resulting machine code is identical to what `maxInt` would have produced — but you only wrote it once.

> **Important:** `T` only needs to support the operations you actually use. `maximum` uses `>` — so it works for anything with an `operator>`. If you try `maximum(circle1, circle2)` and `Circle` has no `operator>`, you'll get a compile error from inside the template body. The error messages take some getting used to.

## 4. Type deduction

In `maximum(3, 7)` you did not write `maximum<int>`. The compiler **deduced** `T = int` from the arguments. This is called **template argument deduction**, and it's why templates feel as natural to call as regular functions.

Deduction works when the arguments give the compiler enough information:

```cpp
maximum(1, 2);            // OK — both int, T = int
maximum(2.5, 1.7);        // OK — both double, T = double
```

Deduction fails when the arguments disagree:

```cpp
maximum(1, 2.5);          // ERROR — int vs double, T cannot be both
```

In that case, write the type out explicitly:

```cpp
maximum<double>(1, 2.5);  // OK — T forced to double; 1 converts to 1.0
```

A common pattern: when you need a specific return type, force it. `maximum<double>(3, 4)` returns `4.0` no matter what.

## 5. Multiple type parameters

Templates aren't limited to a single type. You can have as many template parameters as you need:

```cpp
template <typename A, typename B>
void printPair(const A& first, const B& second) {
    std::cout << "(" << first << ", " << second << ")\n";
}
```

```cpp
printPair(1, "one");        // A = int,    B = const char*
printPair(3.14, true);      // A = double, B = bool
printPair(string("pi"), 3.14);
```

This is exactly how `std::pair<T1, T2>` and `std::map<Key, Value>` are declared.

## 6. Class templates

The same idea applies to entire classes. A **class template** is a blueprint for a class; the actual class is generated when you write `Box<int>` or `Box<string>`:

```cpp
template <typename T>
class Box {
    T contents;
public:
    Box(const T& value) : contents(value) {}
    T get() const { return contents; }
    void set(const T& value) { contents = value; }
};
```

Usage:

```cpp
Box<int>    a(42);
Box<string> b("hello");
Box<double> c(3.14);

a.set(100);
std::cout << a.get();   // 100
```

Each instantiation produces a different type. **`Box<int>` and `Box<string>` are unrelated classes** as far as the type system is concerned — you cannot assign one to the other.

Every container you've used (`std::vector`, `std::list`, `std::map`, `std::shared_ptr`) is a class template. The fact that `vector<Shape*>` and `vector<int>` use exactly the same source code is the point of templates.

## 7. Non-type template parameters

Template parameters can also be **values**, usually integers. The classic example is `std::array<T, N>` where `N` is the array's size — and it's part of the type:

```cpp
template <typename T, int N>
class FixedArray {
    T data[N];
public:
    int size() const { return N; }
    T& operator[](int i) { return data[i]; }
};
```

```cpp
FixedArray<int, 5> a;
FixedArray<int, 6> b;     // <-- DIFFERENT TYPE from a
```

`N` is known to the compiler — the array's size is baked into the type. No heap allocation, no `size_t` member; the size *is* part of the type.

Non-type parameters are great for things that should be checked at compile time: matrix dimensions, buffer sizes, enum-like flags.

## 8. Template specialization

Sometimes the generic version of a template isn't quite right for one specific type. You can provide a **specialization** that overrides the generic for that one type:

```cpp
template <typename T>
void describe(const T& value) {
    std::cout << "generic value: " << value << "\n";
}

// Special-case bool — print true/false instead of 1/0
template <>
void describe<bool>(const bool& value) {
    std::cout << "boolean: " << (value ? "true" : "false") << "\n";
}
```

```cpp
describe(42);     // generic value: 42
describe(true);   // boolean: true     <- specialization used
describe(false);  // boolean: false    <- specialization used
```

When the compiler sees `describe(true)`, it finds the specialization for `bool` and uses that. Everything else still falls through to the generic.

A real-world example: `std::vector<bool>` is famously specialized to pack bools into bits. The interface is the same as `vector<T>`, but the storage is completely different. That's a class-template specialization.

**Use specialization sparingly.** Most of the time, the generic version is what you want. Reach for specialization only when the generic version would be inefficient or wrong for one specific type.

## 9. A tiny generic container — `Stack<T>`

Putting it together: a stack data structure that can hold any type. This is the same shape as the standard library's `std::stack<T>`:

```cpp
template <typename T>
class Stack {
    std::vector<T> data;
public:
    void push(const T& value) { data.push_back(value); }
    void pop()                { if (!data.empty()) data.pop_back(); }
    T&       top()            { return data.back(); }
    const T& top() const      { return data.back(); }
    bool empty() const        { return data.empty(); }
    size_t size() const       { return data.size(); }
};
```

```cpp
Stack<int> ints;
ints.push(1); ints.push(2); ints.push(3);

Stack<string> words;
words.push("first"); words.push("second");
```

One class definition, two completely unrelated container types. The bodies the compiler generates for `Stack<int>` and `Stack<string>` are entirely separate — they just look the same in source code.

## 10. Templates and polymorphism

Templates and inheritance solve **different** problems, and they combine beautifully.

| Mechanism | When the decision happens | Used for |
|---|---|---|
| **Inheritance + `virtual`** | Runtime — depends on the real object | "What does *this particular* `Shape` do?" |
| **Templates** | Compile time — depends on the type written | "Apply this logic to *every* type that supports it" |

Concrete example. We have the usual `Shape` hierarchy:

```cpp
class Shape    { public: virtual void draw() const = 0; };
class Circle   : public Shape { /* ... */ };
class Rectangle : public Shape { /* ... */ };
```

We want a `drawAll` function that can draw any container of `Shape`-like things — raw pointers, `unique_ptr`s, `shared_ptr`s. Without templates we'd need a separate function for each. With templates, one function does it all:

```cpp
template <typename Container>
void drawAll(const Container& items) {
    for (const auto& item : items)
        item->draw();
}
```

```cpp
vector<unique_ptr<Shape>> a = ...;
vector<shared_ptr<Shape>> b = ...;

drawAll(a);   // works
drawAll(b);   // works
```

Inside `drawAll`, `item->draw()` still uses virtual dispatch — the right `Circle::draw` or `Rectangle::draw` runs at runtime. Templates handle the *container variation*; inheritance handles the *object variation*.

This is the modern C++ pattern: **inheritance for "is-a" relationships, templates for "works with any type that has these operations."**

## 11. Where templates live (the header rule)

There's one practical quirk of templates that surprises everyone the first time: **template definitions almost always live in header files**, not in `.cpp` files.

Why? The compiler can only generate the concrete instantiations (`Stack<int>`, `Stack<string>`, …) when it sees both the template definition *and* the call site. If the template body is hidden in a `.cpp` file, other translation units that try to use `Stack<int>` can't see the body and the linker fails.

The simplest pattern, which is what professional codebases use:

```
Stack.h    <- template definition: everything, body included
main.cpp   <- #include "Stack.h", uses Stack<int>
```

You may sometimes see a `.tpp` or `.inl` file `#include`d at the bottom of the header to keep the declarations and definitions visually separate — that's a style choice, but the file is still ultimately included from the header.

**Rule of thumb: write your templates in `.h` files. Don't try to split declaration from definition the way you do for non-template classes.**

(For lab purposes, our `templates.cpp` keeps everything in one file, just like the standard library headers do.)

## 12. Common Mistakes

| Mistake | Why it's bad | Fix |
|---|---|---|
| Putting template implementation in a `.cpp` file | Linker errors when the template is used from another file | Define templates in headers |
| Expecting template error messages to be readable | A small mistake can produce pages of compiler output | Read the first error line; the rest is fallout |
| Assuming `Box<int>` and `Box<double>` are related | They are independent types | Use template inheritance or a non-template base class if you need a common type |
| Mixing argument types without an explicit `<T>` | Deduction fails with "ambiguous template argument" | Write `f<T>(...)` to force the type |
| Forcing every template parameter to be the same type | Limits flexibility | Use multiple template parameters when types should differ |
| Writing a template that requires too much from `T` | Compiles for `int`, fails for `string` with a confusing error | Use only operations the template's contract actually documents |
| Specializing without good reason | Adds maintenance burden, hides surprising behaviour | Stick with the generic unless a specific type really needs different code |
| Forgetting `typename` before a dependent type | `typename T::iterator` is required inside templates | Add the `typename` keyword when the type depends on a template parameter |

### Exercise 1 — `minimum` ⭐

Mirror the `maximum` template from §3, but return the smaller of two values:

```cpp
template <typename T>
T minimum(T a, T b);
```

Call it with `int`, `double`, and `string` and check that all three work without writing the type explicitly.

### Exercise 2 — Generic `swap` ⭐

Write a function template `swapValues(a, b)` that swaps two variables of the same type. It should work for `int`, `double`, `string`, and any class that supports assignment. (Yes, the standard library has `std::swap` — write your own as practice.)

### Exercise 3 — `Pair<A, B>` ⭐⭐

Write a class template `Pair<A, B>` with:

- two public-accessible members `first` and `second`,
- a constructor that takes an `A` and a `B`,
- a `print()` method that writes `(first, second)` to `cout`.

Then create:
```cpp
Pair<int, std::string> p1(1, "one");
Pair<std::string, double> p2("pi", 3.14);
p1.print();
p2.print();
```

### Exercise 4 — Bounded `Stack<T, N>` ⭐⭐

Extend the `Stack<T>` template from §9 with a compile-time capacity using a non-type parameter:

```cpp
template <typename T, int Capacity>
class Stack { /* ... */ };
```

`push` should refuse (throw `std::overflow_error`) when the stack is already full. Two stacks with the same `T` but different `Capacity` should be **different types** — verify that by trying to assign one to the other (it must not compile).

### Exercise 5 — Specialize for `double` ⭐⭐⭐

Take the `describe` function from §8:

```cpp
template <typename T>
void describe(const T& value);
```

Add a specialization for `double` that prints the value with exactly two decimal places (e.g., `3.14`, `2.50`). Show that `describe(3)` still uses the generic version and `describe(3.0)` uses the specialization.

### Exercise 6 — Combine with smart pointers ⭐⭐⭐

Write a function template

```cpp
template <typename T, typename... Args>
std::unique_ptr<T> makeShape(Args&&... args);
```

…that does the same thing as `std::make_unique<T>`. It should let you write `makeShape<Circle>(5.0, "red")` and get back a `unique_ptr<Circle>`. (This exercise previews **variadic templates** and **perfect forwarding** — read up on `std::forward` if you get stuck.)

## 14. Quick Recap

| Concept | What it is | Example |
|---|---|---|
| **Function template** | A function recipe parameterised over types | `template<typename T> T max(T a, T b);` |
| **Type deduction** | Compiler figures out `T` from arguments | `max(1, 2)` deduces `T = int` |
| **Multiple type params** | More than one `typename` | `template<typename A, typename B>` |
| **Class template** | A class blueprint parameterised over types | `template<typename T> class Box {...};` |
| **Non-type parameter** | A value (usually `int`) as a template parameter | `template<typename T, int N> class FixedArray;` |
| **Specialization** | Override the generic for a specific type | `template<> void describe<bool>(...)` |
| **Templates + virtual** | Templates handle type genericity, virtual handles runtime dispatch | `drawAll(vector<unique_ptr<Shape>>)` |
| **Header rule** | Put template definitions in headers | One `.h` file holding declarations *and* bodies |
